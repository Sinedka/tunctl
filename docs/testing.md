# Проверка сборки и сети

Основная платформа проверки — x86_64-linux. `nix flake check` собирает пакет, запускает CTest, строит Home Manager generation и загружает NixOS в QEMU. Внутри VM тест создаёт ещё один network namespace с veth, OpenVPN-сервером, DNS и HTTPS. CA, клиентский и серверный ключи создаются заново внутри гостя. Тест обходится без аккаунта VPN-провайдера.

| Возможность | Как проверяется |
|---|---|
| C++23, CLI и TUI | Сборка CMake, установка двух бинарников. VM открывает TUI от обычного пользователя в PTY, переключает экран и завершает его клавишей q. Полная визуальная проверка раскладки на всех размерах терминала остаётся ручной. |
| Безопасный импорт | Unit-тесты блоков, запрещённых директив, относительного файла с пробелом, tls-auth с направлением, выхода через symlink и некорректного ZIP. VM импортирует директорию с несколькими профилями. Также выполнена локальная офлайн-проверка архива с 40 профилями. |
| Серверы | VM задерживает ответ сервера до запуска OpenVPN и проверяет блокирующий маршрут до появления TUN. Затем она проверяет подключение и переключение на второй профиль. Нерабочий endpoint вызывает rollback с проверкой выбранного имени и текущего handshake. Групповые измерения, поиск, сортировка и редактирование страны требуют интерактивной приёмки. |
| IPC | Unit-тест кадра JSON. В VM пользователь-оператор получает status и отправляет правила, аккаунт без доступа к socket получает отказ. Отдельный аккаунт с доступом к socket, отсутствующий в operators, получает отказ по SO_PEERCRED. Невалидный CIDR отклоняется с сохранением предыдущего работающего правила. |
| Маршрут по умолчанию | VM проверяет ip rules обоих семейств, lookup с VPN-меткой и реальный обмен по TLS через TUN. Сервер возвращает увиденный IP клиента. |
| Kill switch | При разорванном VPN проверяются фактический отказ ping обычному адресу и успешный ping DIRECT. Отдельная проверка блокирует IPv6 по veth. Полноценное IPv6-соединение с dual-stack провайдером требует отдельного испытания. |
| DNS routing | Локальный запрос через dnsmasq, появление адреса в nft set, запрос HTTPS физическим путём и исчезновение адреса после TTL. Проверяется разрешение имени самого VPN через отдельный bootstrap. Внешние DNS/DoH-сервисы не являются зависимостью теста. |
| Приложения | Пользовательская systemd scope, обновление nft-правил до открытия сокета и пакет до физического peer при отключённом VPN. При конфликте правила приложения VPN с DIRECT CIDR проверяется отказ при выключенном туннеле. Реальные GUI Firefox, Telegram и Steam в VM не запускаются. |
| Изменение физической сети | VM опускает, переименовывает и поднимает uplink, проверяет пакеты через TUN. Отдельно убивает OpenVPN и ожидает нового handshake. Переключение между реальными точками Wi-Fi и suspend/resume остаются аппаратными проверками. |
| Ping, потери и jitter | Парсер проверяется тестовой выборкой. В VM исполняется ping через TUN, проверяются число ответов и измеренный RTT. |
| Скорость и публичный IP | HTTPS-сервер в namespace принимает POST и отдаёт известный объём данных. Проверяются upload, download и исходный адрес VPN. Отдельный POST проходит через DIRECT после переименования физического интерфейса. Тест измеряет передачу внутри VM. Производительность интернет-провайдера и доступность публичных тестовых сервисов проверяются пользователем. |
| Home Manager | Собирается конфигурация с IP, доменным и прикладным правилами, desktop entry и build-time проверкой JSON. VM отдельно проверяет отправку правил backend. Вход в графическую сессию, пользовательские темы, сброс и экспорт overrides остаются ручными сценариями. |
| Boot и удаление | VM проверяет запуск socket и routing при загрузке. Автоподключение сохранённого профиля при повторной загрузке, откат поколения и удаление на существующем хосте требуют отдельной проверки. |

## Переносимые файлы для Linux

Сборка в Debian 12 x86_64 запускает три теста CTest и проверяет запуск упакованного AppImage. Сквозной сценарий устанавливает backend из указанного файла в пустой контейнер с systemd, включает kill switch, валидирует и импортирует профиль с внешними сертификатами от имени оператора. После TLS handshake тест проверяет HTTP-ответ по TUN и отключает VPN.

Для версии 0.1.0 этот сценарий прошёл с AppImage на Debian 13 и с tar.gz на Arch Linux. На обеих системах проверен обычный запуск AppImage через FUSE 3, на Arch также проверены открытие TUI и ввод клавиш в псевдотерминале. Повторная установка переносимой версии в Debian сохранила политику и включённые службы. Готовые артефакты проверены на x86_64.

Для воспроизведения подготовьте локальный образ Debian 13 или Arch с systemd и зависимостями backend из [руководства для Linux](linux.md), bash, openssl и util-linux. Команды выполняются из корня проекта. Для прогона архива подставьте имя `.tar.gz` в `release`. Каждый тест использует новый контейнер.

```sh
image=localhost/vpnctl-test
release=vpnctl-0.1.0-x86_64.AppImage
podman run -d --name vpnctl-native-test --systemd=always --network=none \
  --device=/dev/net/tun --cap-add=NET_ADMIN --cap-add=SYS_ADMIN \
  -v "$PWD/tests/native_tunnel.sh:/native-test:ro" \
  -v "$PWD/build/portable:/files:ro" "$image" /usr/lib/systemd/systemd
podman exec vpnctl-native-test bash /native-test "/files/$release"
podman rm -f vpnctl-native-test
```

В rootless-контейнере с запрещёнными ICMP-сокетами пользовательский `ping` возвращает ошибку прав. Поэтому нативный тест проверяет передачу данных по TCP. Ping через TUN дополнительно проверяется в NixOS VM. Инструкции сборки и первого запуска приведены в [руководстве для Linux](linux.md).

## Воспроизведение на NixOS

```sh
nix build
nix flake check -L
nix build -L .#checks.x86_64-linux.vm
nix build .#checks.x86_64-linux.home
nix flake check --all-systems --no-build
nix develop -c cmake -S . -B build/dev
nix develop -c cmake --build build/dev
nix develop -c ctest --test-dir build/dev --output-on-failure
```

Для aarch64-linux вычислены derivations. Для нативной сборки и запуска VM выполните `nix flake check -L` на aarch64 Linux builder с поддержкой виртуализации.

Для ручной проверки пользовательских настроек задайте в HM адрес `192.0.2.1/32`, синхронизируйте его, измените действие в Routing и проверьте конфигурацию через `vpnctl export`. Запустите `vpnctl reset` и сравните результат с исходным JSON. Проверьте работу приложения из desktop entry, затем сравните cgroup его основного и дочернего процессов в `/proc/PID/cgroup`. При проверке удаления сохраните вывод `ip rule`, `ip route`, `nft list tables` и текущего резолвера до установки и сравните с состоянием после применения прежнего поколения.
